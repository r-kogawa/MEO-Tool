# 05. 不足点・未決事項・リスク

優先度: **🔴 仕様確定前に要判断** / 🟡 実装着手前に要判断 / 🟢 後から決めてよい

## A. ポリシー・法務（最優先）

| ID | 優先 | 内容 | なぜ問題か | 対応案 |
| --- | --- | --- | --- | --- |
| I-01 | 🔴 | **条件を満たした人だけを Google 口コミに誘導する設計（R-1）** | Google のポリシーは「高評価の顧客だけに口コミを依頼すること」を**レビューゲーティング**として禁止している。違反時は口コミの削除、プロフィールの制限・停止のおそれがある | ① すべての回答者に Google 投稿導線を出し、条件は「下書きを生成するかどうか」だけに使う ② 条件不一致の人には「店舗へのご意見」を主、Google 投稿を従として表示する ③ 現行要件のまま進める場合は、リスクを顧客に明示し合意を取る。**どれを採るか要判断** ／ 2026-10-08: 遷移ルール（評価に応じた口コミ投稿の案内）はレビューゲーティングにあたるリスクを承知のうえで実装した。判定はサーバーだけで行う（docs/superpowers/specs/2026-10-08-surveys-integration-design.md） |
| I-02 | 🔴 | **口コミ文章を生成して提示すること（R-2）** | 景品表示法のステルスマーケティング規制（2023 年 10 月施行）では、事業者が口コミの内容決定に関与すると事業者の広告と見なされうる。Google も「実際の体験に基づかない投稿」を禁止している | ・生成の材料を**回答者本人の回答だけ**に限定する（F-08 の生成方針） ・「下書きです。ご自身の言葉で自由に編集してください」を明示し編集を前提にする ・店舗が伝えたい特徴を生成に混ぜる機能（`storeHighlights`）の可否を法務確認する ・投稿の見返り（割引・特典）とは**絶対に**組み合わせない |
| I-03 | 🔴 | 法務・規約の確認体制 | I-01 / I-02 は顧客（店舗）側の法的リスクにもなる | 弁護士確認、サービス利用規約に「利用者（店舗）の責任で Google ポリシー・法令を遵守する」旨を明記 |
| I-11 | 🟡 | 回答者の個人情報 | 自由記述に個人情報が入る可能性、IP / UA の扱い。氏名・連絡先を集めるなら取扱いが大きく変わる | 回答画面にプライバシーポリシーへのリンク、IP / UA はハッシュのみ保存（設計済み）、保存期間を決める |

## B. 技術的な制約（要件の書き方と実現方法がずれる箇所）

| ID | 優先 | 内容 | 詳細 | 対応案 |
| --- | --- | --- | --- | --- |
| I-04 | 🔴 | **生成した文章を Google に渡して遷移することはできない** | 口コミ投稿 URL（`writereview?placeid=`）に本文を入れるパラメータはない。GBP API も「顧客として口コミを投稿する」機能は提供していない | クリップボードにコピー → 遷移 → 回答者が貼り付け（F-13 で設計済み）。貼り付け手順を画面で案内する。**要件の表現を「文章をコピーして遷移する」に修正して合意する** |
| I-05 | 🔴 | **GBP API は利用申請と承認が必要** | GBP API は申請して承認されるまでクォータが 0。加えて `business.manage` は機微スコープのため、本番公開には OAuth 同意画面の審査が必要。どちらも数週間かかることがある | 早い段階で GCP プロジェクトを作って申請する。審査中はテストユーザー（上限 100 名）で開発する |
| I-06 | 🟡 | LLM の提供元・モデル・コスト | 提供元（Gemini / Claude / OpenAI など）、1 件あたりの費用、データの学習利用の有無 | アダプタで差し替え可能にしたうえで 1 つ選ぶ。月間上限と単価から原価を試算する ／ 2026-10-08: 口コミ文面の生成（LLM）は今回は作らない |
| I-07 | ✅ 決着 | **検索順位を取得する公式 API がない** | Google マップのローカル検索順位を返す公式 API はない。Places API（Text Search）は近い結果を返すが Google マップの表示と一致しない。Google の検索結果のスクレイピングは利用規約違反 | ~~① Places API で近似する（安価・規約上安全・精度は近似）② SERP API 事業者を使う（精度は高いが従量課金・事業者の規約確認が必要）。精度・費用・計測頻度・キーワード上限を決めて選ぶ。どちらでも「実際の表示と異なる場合がある」旨を画面に出す。Places API を使う場合の保存制限は I-26~~ **2026-10-08: 自前で Google マップをスクレイピングする方式に決定（Functions 上の Headless Chrome）。規約違反とブロックのリスクを承知のうえで採用し、`RankProvider` で SERP API などに差し替えられるようにした（`docs/superpowers/specs/2026-10-08-rank-scraping-design.md`）。** |
| I-26 | ✅ 解決 | ~~**Places API の取得データは place ID 以外保存できない**~~ | 順位計測で Places API を使わなくなったため対象外。計測結果の 20 件（店名・評価など）は自前で取得したデータとして `rankResults` に保存する | 2026-10-08 解決。取得元を SERP API 事業者に替える場合は、その事業者の規約で保存可否を確認し直す |
| I-19 | ✅ 解決 | ~~「検索順位の**検索**」の意味~~ | 登録済みキーワードの定期計測か、任意キーワードのその場検索か | 2026-10-08 解決。その場計測（`/rankings/search`）を実装したため、定期計測・手動計測とあわせて両方に対応した |
| I-27 | 🟡 | **口コミ件数を取得できない場合がある** | headless の Chrome で Google マップを開くと、一覧のカードに口コミ件数が出ないことがある（2026-10-08 確認）。その場合 `reviewCount` は `null` とし、画面には「—」を出す。bot 検知を回避する手段（UA の偽装など）は使わない方針とした | 件数を確実に取りたい場合は、`RankProvider` を SERP API に差し替える。画面は「—」の表示に対応済み |
| I-28 | 🟢 | 結果なしの判定文言と店舗ページへの直接移動が未確認の部分がある | 「結果なし」は「が見つかりません」で判定している。1 件だけ一致して店舗ページへ直接移動する経路（place 経路）は、実画面で再現できず未確認（「渋谷区役所」は一覧で返った） | 定期的に `npm --prefix functions run rank:probe` で実画面を確認する。画面構造の変更で取得が止まったら `gmapsScraper.ts` / `parseGmapsItems.ts` を直す |
